2.1这个任务想让你学会什么

普通模型调用接收问题并生成回答。加入工具后，模型可以提出调用请求，由 Python 程序执行函数，再把执行结果交回模型，继续完成回答。本任务从这条最小流程入手，理解一个智能体如何连接模型、工具和对话状态。

参考项目保留了逐步构建的代码：local.py 尝试本地模型，ds.py 到 ds6.py 逐步接入云端模型、扩展工具和交互方式，当前版本再加入知识库与 SQLite 存储。可以先阅读示例，再自己修改和补充，不要求首次参加就从空文件重写全部功能。

完成第一个小任务后，你应能解释模型与 Python 工具如何配合、多轮历史如何组织、重启后如何恢复记录，以及上下文压缩与网页交互如何实现，最终交付一个可以在浏览器中使用的助手。

2.2需要什么基础

开始前需要会的

  • 能读写简单的 Python 函数，理解参数、返回值、列表和字典
  • 会在终端运行 Python 文件，能安装依赖并阅读基本报错
  • 知道文件和目录的区别，能用编辑器修改代码

可以边做边学的

  • API 地址、密钥、环境变量和 .env 文件
  • async、await 和流式输出的基本用法
  • Agent、工具调用、上下文、Embedding 和 RAG 的含义

第一次不用先会的

  • 不要求训练模型，也不要求深度学习推导
  • 不要求先掌握向量数据库，阶段 5 才用到
  • 不需要独立前端开发，网页用 Gradio 搭建

Start · 起步练习

先跑通模型，再改一个自己的工具

这三步对应 local.py 到 ds.py 的过程，是进入阶段 1—4 之前的检查点：先看见模型怎么被调用，再看见工具怎么被真正执行。

步骤1

观察一次本地模型调用

src/local.py ↗

它用 Ollama 的本地模型回答一个固定问题。

  • 按 README 的包装命令运行示例，确认使用的是 Chat Completions 接口
  • 把固定问题改成自己的问题，保留修改前后的输出
  • 找出代码里定义模型、设置指令、发起请求和输出结果的位置
验收时能指出：模型运行在哪里，请求发到哪里，以及修改问题后输出发生了什么变化。
步骤2

切换到云端模型，观察时间工具

src/ds.py ↗

它接入云端模型、注册时间工具，并流式输出回答。这个版本使用固定问题，还没有终端多轮输入。

  • 配置自己的服务地址与密钥，核对服务商提供的模型名称
  • 运行时间查询示例，记录 Python 工具实际执行的证据，例如工具内的调试输出
  • 用自己的话画出或写出流程：问题 → 模型提出调用 → Python 执行 → 返回工具结果 → 模型回答
验收不只看回答是否出现时间，还要能确认工具确实运行过。
步骤3

自己修改一个工具

增加一个简单工具，或把已有工具改成带参数的版本。例如：输入科目和学习时长，按你写的固定规则返回学习安排。工具规则由 Python 明确实现，便于对照输出是否符合预期。

准备好三组问题：

问题类型观察重点
明确需要工具的问题模型是否选择工具，参数和返回值是否正确
不需要工具的普通问题模型是否出现多余调用
缺少参数或表述模糊的问题模型是追问、补猜参数，还是调用失败
不要预设模型每次都会选对。出现失败同样可以交付，但需要保留记录并解释你观察到的现象。
三步完成后，保留可运行代码与三组工具调用记录，再进入下面的阶段 1—4。

Build · 阶段 1—4

四个阶段，把终端脚本变成网页助手

这四个阶段都属于第一个小任务。每个阶段保留能运行的版本和简短记录，可以随时向接应人反馈进度；完成阶段 4 后统一提交第一次交付材料。

阶段1

让程序支持连续对话

src/ds2.py ↗

做什么：加入终端输入循环，把用户消息和助手回答保存到列表，下一轮继续传给模型。

  • 设计一次「先提供信息，再追问」的对话
  • 分别保留历史和清空历史，比较两次回答
  • 退出程序再启动，观察内存中的记录是否还在
交付与验收：提交多轮对话代码和两组对照记录，解释为什么这时的记忆无法跨进程保存。
阶段2

扩展工具，并观察调用约束

src/ds3.py ↗ src/ds4.py ↗

做什么：学习联网搜索、文件读写和调用过程展示，比较自动选择工具与强制调用工具的行为。

  • 在专门的测试目录中完成一次文件读取和写入；有 Tavily Key 时再试联网搜索
  • 用相同的普通问题和工具问题，比较开启、关闭 tool_choice="required" 后的结果
交付与验收：提交至少三组对照记录，说明强制调用是否带来多余操作，并指出早期路径检查的局限。未配置搜索服务时，说明跳过部分及原因。
注意：旧版文件工具可能覆盖文件，ds3.py 没有目录限制，ds4.py 的路径检查也不构成完整隔离。实验只使用可覆盖的测试文件。
阶段3

保存历史，压缩较早的对话

src/ds5.py ↗

做什么：用 JSON 保存聊天历史，重新启动后读取；对较早的消息生成摘要，保留近期原文。

  • 验证重启后能否继续对话
  • 让上下文达到压缩条件，比较压缩前后保留的信息
  • 尝试清空历史
交付与验收：提交脱敏的历史样例、一组摘要前后对照，并指出至少一个摘要保留的信息和一个可能丢失的细节。能解释「存盘」和「发给模型的上下文」有什么区别。
该示例超过 12 条消息时压缩，保留最近 4 条原文；「消息条数」与「对话轮数」需要区分。
阶段4

做一个能操作的网页界面

src/ds6.py ↗

做什么：用 Gradio 替代终端交互，显示流式回答、历史和清空入口。

  • 在浏览器中完成输入、连续提问和清空操作
  • 说明页面显示的内容与下一轮发送给模型的内容分别是什么
  • 服务没有返回过程事件时如实记录，不要求额外生成「思考过程」
交付与验收：提交运行步骤、页面截图或简短演示，能够演示多轮对话和清空。说明 ds5.py、ds6.py 共用历史文件时可能产生的影响。

Next · 进阶方向

做完基础构建之后，还可以往哪里走

以下方向不属于第一次交付要求。部分能力已有初步实现，仍需要系统验证和改进。

1 · 安全相关的测试与思考

  • 文档或工具返回内容里夹带指令时，模型会不会把资料当成命令
  • 混入错误资料后，检索、回答与引用会受到什么影响
  • 文件路径限制能否阻止越界访问；写入、覆盖或删除是否需要执行前确认

2 · 优化结构，进一步解耦

  • 继续分离网页交互、对话编排与业务逻辑，明确模块的输入输出
  • 只选一处耦合，例如把聊天处理逻辑从界面回调里提出来
  • 画出修改前后的依赖关系，并证明原有功能仍能运行

3 · 迁移到 LangChain

  • 先迁移一条最小流程，再逐步覆盖记忆和引用
  • 保留原实现作对照，用相同问题与资料检查结果
  • 记录框架在接口、状态管理和调试方式上的差异
安全小实验的做法：先选一个问题，用隔离目录、自编资料和模拟工具做正常输入与异常输入的对照，记录预期行为、实际行为、失败位置和改进建议，再用相同样例复测。现有删除确认和路径检查可以作为起点，不应直接视为完整安全方案。迁移框架时也不预设迁移后效果一定更好。
